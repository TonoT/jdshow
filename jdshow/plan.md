# JDShow（Job Radar）项目实施计划

> 文档状态：第一阶段 MVP 规划稿  
> 更新日期：2026-08-10  
> 当前项目状态：`jdshow` 目录为空，未发现已有源码、配置、测试或文档。因此本计划没有需要迁移或兼容的既有实现，后续从最小可运行骨架开始增量建设。

## 1. 项目目标

JDShow 是面向求职者的招聘雷达，第一阶段聚焦中国互联网及科技相关岗位。系统通过合规的数据来源自动发现岗位，统一数据格式，识别新增、更新和下架状态，并提供可搜索、可筛选、可追溯的网站。

第一阶段目标：

- 接入少量、稳定、经过合规确认的公司官方招聘来源，跑通端到端链路。
- 形成可扩展的数据源 Adapter 机制，新增来源时不修改采集核心流程。
- 建立公司、岗位、来源、采集记录、版本和人工修正等基础数据模型。
- 正确处理重复采集、岗位更新、跨来源重复候选和岗位失效。
- 提供首页、岗位搜索、岗位详情和公司详情等公开页面。
- 从第一版落实输入校验、限流、审计、配置管理、备份和可观测性。
- 为岗位订阅、AI 匹配、消息通知和招聘趋势保留清晰扩展点，但不提前实现。

成功原则：数据来源合法可追溯、岗位状态可信、网站可稳定运行、增加新来源成本可控。

## 2. MVP 功能范围

### 2.1 数据采集

- 首批接入 2～3 个已确认允许访问、具有公开职位页面或官方接口的公司来源。
- 采集社会招聘中的科技岗位；暂不追求公司数量和全量历史数据。
- Adapter 实现岗位列表发现、详情获取、解析、标准化和来源标识。
- 支持定时运行、手动触发、失败重试、超时、低频限速和采集结果统计。
- 保存来源 URL、原始外部职位 ID、首次发现时间、最后发现时间及原始数据快照或摘要。

### 2.2 数据治理

- 公司名称、城市、招聘类型、学历、经验、薪资和岗位方向标准化。
- 来源内确定性去重，跨来源生成重复候选；低置信度结果不自动合并。
- 管理岗位 `NEW`、`ACTIVE`、`UPDATED`、`EXPIRED`、`REMOVED` 状态。
- 支持公司元数据及标签的来源、置信度、最后核验时间和人工修正。
- 提供最小管理员能力：登录、查看采集运行、修正公司/岗位、处理重复候选、审计操作。

### 2.3 网站与 API

- 首页：最新岗位、今日新增、最近新增、热门公司和热门岗位方向。
- 岗位搜索：关键词、公司、城市、薪资、经验、学历、行业、方向、来源和发布时间筛选。
- 岗位详情：标准化信息、职责要求、公司摘要、来源和原始招聘链接。
- 公司详情：简介、可追溯标签、当前岗位和历史岗位数量。
- 面向页面的只读 HTTP API 或服务端查询接口；公开接口必须分页、限流并限制最大结果集。
- 健康检查、就绪检查和内部指标端点。

## 3. 非 MVP 功能

第一阶段明确不实现：

- 简历上传、简历解析、AI 岗位匹配和 AI JD 分析。
- 用户注册、收藏、个性化推荐、岗位订阅和消息推送。
- 招聘趋势预测、完整 BI 报表和数据导出平台。
- 原生移动 App、小程序和多语言站点。
- Kubernetes、Kafka、微服务、分布式工作流引擎和独立数据湖。
- 绕过登录、验证码、付费墙、访问控制或反爬机制的采集方式。
- 账号池、代理池规避封禁、高频并发抓取。
- 未获得公开或授权获取方式的招聘平台采集。
- 大规模自动判定“外包公司”等敏感标签；只能使用可验证来源或人工确认。

## 4. 整体系统架构

采用模块化单体，Web 与 Worker 共用代码库，可作为不同进程启动：

```text
公开浏览器 / 管理员
        |
   CDN / WAF / TLS
        |
   Go HTTP Server
        |
  +-----+-----------------------------+
  | 页面/API | 管理 | 搜索 | 公司/岗位 |
  +-----+-----------------------------+
        | Application Services
        |
     PostgreSQL
        ^
        |
  Background Worker
        |
 Scheduler -> Source Adapter -> Fetcher -> Parser
           -> Normalizer -> Deduplicator -> Storage
```

核心边界：

- `source`：来源定义、Adapter 接口和各来源实现。
- `ingest`：采集编排、原始数据保存、标准化、去重和状态更新。
- `job` / `company`：领域模型与业务规则。
- `search`：筛选、排序和关键词查询。
- `admin`：人工修正、重复候选处理和审计。
- `platform`：数据库、HTTP 客户端、日志、指标、配置和调度。

MVP 不引入消息队列。定时任务写入 PostgreSQL 任务表，由 Worker 使用行锁领取；Web 与 Worker 可先部署在同一台主机的不同容器中。任务量或解耦需求达到明确指标后，再评估 Redis 队列。

## 5. 技术选型及原因

### 5.1 后端

- **Go（采用开发时稳定版本，并在 `go.mod` 固定）**：符合主语言要求，适合 HTTP 服务和受控并发采集。
- **`net/http` + `chi`**：路由能力足够、依赖轻、易测试；不需要大型 Web 框架。
- **`pgx` + `sqlc`**：保留显式 SQL 和类型安全，适合搜索及去重查询；避免重 ORM 隐藏行为。
- **`goose` 或同类轻量迁移工具**：数据库变更可审计、可重复执行。
- **Go `html/template` + 少量渐进增强脚本**：MVP 以服务端渲染为主，减少前后端双工程和部署复杂度。交互复杂度增长后再评估独立前端。
- **`robfig/cron`**：仅负责产生周期任务；实际任务状态持久化在 PostgreSQL，避免进程重启丢失执行记录。
- **结构化日志（`log/slog`）**：使用 Go 标准能力输出 JSON 日志。
- **Prometheus 指标格式**：采集次数、失败率、延迟、岗位变化量和 HTTP 指标可被常见监控系统采集。

具体第三方库在项目初始化任务中做一次小型技术验证后锁定版本，不在规划阶段固定未经验证的版本号。

### 5.2 数据与搜索

- **PostgreSQL**：承担事务数据、任务队列、审计和 MVP 搜索，减少组件数量。
- **PostgreSQL `pg_trgm` + 标准化关键词/标签**：用于公司名、岗位名等模糊匹配。中文全文检索需验证分词效果；MVP 可先使用标题、标签、技能词和描述的受控查询。
- **Redis：MVP 可选**。仅当多实例限流、热点缓存或任务吞吐确有需要时引入；单实例初期可使用进程内限流并由 CDN/WAF 提供边缘保护。
- **独立搜索引擎：非 MVP**。当 PostgreSQL 搜索在相关性或性能上不满足验收指标时，再评估 Meilisearch/OpenSearch，并通过 `search` 接口隔离迁移。

### 5.3 部署

- **Docker Compose**：本地和单机部署包含 `web`、`worker`、`postgres`，可选 `redis`、`prometheus`。
- **反向代理/CDN/WAF**：生产环境终止 TLS、提供边缘限流和基础 DDoS 防护。

## 7. 数据库设计

### 7.1 核心表

- `companies`：公司主实体和展示字段。
- `company_aliases`：中文名、英文名、历史名及来源别名，用于归一和匹配。
- `company_metadata`：结构化公司属性、值、来源、置信度和核验时间。
- `company_tags`：标签、标签类型、证据来源、置信度和人工锁定状态。
- `sources`：数据源配置、来源类型、合规状态、调度策略和启停状态。
- `jobs`：归一化岗位主实体，表示用户看到的一条岗位。
- `job_sources`：岗位与来源记录的关联；保存外部 ID、来源 URL、时间和来源状态。
- `job_versions`：职责、要求、薪资等规范字段变化的版本或差异摘要。
- `job_skills`：岗位技能词及提取方式、置信度。
- `locations`：城市及标准行政区信息；MVP 也可先作为受控字典表。
- `crawl_runs`：每次来源采集运行、状态、统计、错误摘要和耗时。
- `crawl_items`：单条发现记录、处理结果和错误；原始响应按保留策略存摘要或受控快照。
- `ingest_tasks`：持久化后台任务、重试次数、可执行时间、锁和状态。
- `duplicate_candidates`：跨来源疑似重复、分数、理由和处理结果。
- `manual_overrides`：人工覆盖的字段、原值、新值、原因和有效性。
- `admin_users`、`roles`、`admin_user_roles`：管理员认证与 RBAC。
- `audit_logs`：管理员和系统关键操作审计。

### 7.2 数据库约束与索引

- 所有业务表使用内部不可枚举 ID（UUID/UUIDv7 或数据库生成标识，初始化时验证选择）。
- `job_sources (source_id, external_job_id)` 在外部 ID 存在时建立唯一约束。
- 外部 ID 不存在时，对 `(source_id, canonical_url_hash)` 建立受控唯一约束。
- `jobs` 对 `company_id`、`status`、`published_at`、`last_seen_at`、城市和岗位方向建立组合索引。
- `crawl_runs`、`ingest_tasks` 按状态和计划执行时间建立索引。
- JSONB 仅存来源扩展字段和原始载荷，不替代稳定业务列。
- 时间统一存 UTC，展示层转换为 `Asia/Shanghai`。
- 迁移必须同时提供向前迁移；破坏性回滚是否支持按变更风险决定。

### 7.3 保留策略

- 岗位版本和来源生命周期记录长期保留，用于状态追踪。
- 原始响应可能包含版权内容，应仅保存处理所需字段或受控快照，并确认来源条款。
- 采集成功明细、失败明细和日志按配置周期清理，默认建议 30～90 天，最终值待确认。
- 审计日志只追加，不允许普通管理员修改。

## 8. 公司信息模型

`Company` 建议包含：

```text
id, canonical_name, english_name, logo_url, website_url,
founded_at, headquarters, employee_size, industry, company_type,
listing_status, description, created_at, updated_at
```

对“是否外包、是否国企、是否央企、是否外企、是否互联网公司、是否 AI 公司”等可争议属性，不直接使用不可追溯的布尔值作为唯一事实。使用 `company_metadata` / `company_tags` 表达：

```text
company_id
key 或 tag
value
source_type          # official / public_registry / partner / manual / model_suggestion
source_url
confidence           # 0～1；人工确认可单独标识，不简单等同于 1
last_verified_at
verified_by
is_manual_override
notes
```

规则：

- 官方公司信息、权威公开名录和人工核验优先级高于自动推断。
- 大模型只能提出待审核建议，不直接写入已验证标签。
- 人工覆盖必须记录原因、操作者和审计日志，并防止下一次采集覆盖。
- Logo 只使用允许展示的官方资源或自有缓存；授权和缓存策略待确认。

## 9. 岗位信息模型

`Job` 主实体建议包含：

```text
id, company_id, title, normalized_title, department,
recruitment_type, headcount, status, status_changed_at,
published_at, source_updated_at, first_seen_at, last_seen_at,
experience_min_years, experience_max_years,
education_level, salary_min, salary_max, salary_months,
salary_currency, salary_period,
responsibilities, requirements, qualifications, benefits,
job_category, description_hash, created_at, updated_at
```

关联模型：

- `job_sources`：`source_name`、`source_url`、`source_type`、`external_job_id`、`first_seen_at`、`last_seen_at`、`published_at`、`source_updated_at`、来源状态。
- `job_locations`：一个岗位可对应多个城市、区域或远程模式。
- `job_skills`：标准技能名、原始词、提取方式和置信度。
- `job_versions`：版本号、内容 Hash、变化字段、采集运行和生成时间。

字段缺失时保存 `NULL`，不使用“未知”“面议”混入数值列；展示层负责友好表达。原始文本和标准化结果并存，保证可追溯和可重新处理。

## 10. 数据源与采集 Adapter 设计

### 10.1 来源合规状态

每个 `Source` 必须先登记：

```text
source_type
base_url
acquisition_method     # official_api / public_page / rss / partner / user_submission
terms_review_status    # pending / approved / rejected
robots_reviewed_at
allowed_paths
request_policy
owner
last_verified_at
```

只有状态为 `approved` 的来源允许在生产环境自动运行。

- 公司官方招聘站：逐个验证公开接口、robots 和条款后接入。
- BOSS 直聘、前程无忧、智联招聘：**待确认数据获取方式**。在获得官方 API、开放平台或明确授权前，不实现自动采集。
- 替代方案：企业官网、官方 RSS/公开职位接口、合作数据源、用户提交职位链接。
- 国企/央企及外企官网：先建设候选公司库与招聘入口登记，不等同于默认获准抓取。

### 10.2 Adapter 接口

概念接口如下，实际签名在实现任务中结合首个来源验证：

```go
type Adapter interface {
    Source() SourceMetadata
    Fetch(ctx context.Context, cursor Cursor) (FetchResult, error)
    Parse(ctx context.Context, payload RawPayload) ([]RawJob, error)
    Normalize(ctx context.Context, raw RawJob) (NormalizedJob, error)
}
```

职责约束：

- `Fetch` 只负责合规请求、分页、游标和响应元数据。
- `Parse` 将来源格式转为来源级结构，保留原值和外部 ID。
- `Normalize` 映射到统一字段，不直接决定跨来源合并。
- 核心流水线负责持久化、幂等、去重、状态变更和指标。
- 公共 HTTP 客户端统一设置 User-Agent、超时、响应大小上限、重试、来源级限速和域名白名单。
- 只对超时、限流和临时服务错误做有上限的指数退避；解析错误不盲目重试。
- 首批来源最终名单、请求频率和条款允许范围均为**待验证**。

## 11. 数据标准化方案

标准化流程：

1. 校验必需字段：公司、标题、来源 URL，以及外部 ID 或可稳定识别信息。
2. 清理 Unicode 空白、HTML 和不可见字符；HTML 使用解析器和白名单，不使用正则粗暴处理。
3. 公司名通过别名表映射到主公司；无法确定时进入待审核队列。
4. 地点映射到标准城市/行政区，保留原始地点文本和“远程/混合办公”信息。
5. 标题生成 `normalized_title`，并映射岗位方向；原始标题永不覆盖。
6. 薪资解析为币种、周期、上下限和发薪月数；无法可靠解析时保留原文，数值字段为空。
7. 经验和学历映射为受控枚举；“不限”“应届”等作为明确枚举处理。
8. 招聘类型映射为社招、校招、实习、合同等；MVP 默认只展示已确认的社招科技岗位。
9. 技能词优先使用可维护字典和规则提取；AI 提取属于后续能力，结果必须带方法和置信度。
10. 生成标准化内容 Hash 和标准化版本号，规则升级后支持离线重处理。

标准化规则需要夹具测试，覆盖中文、英文、中英混合、多地点、面议薪资和缺失字段。

## 12. 去重策略

去重分两层进行，避免误合并。

### 12.1 来源内幂等

按以下优先级识别同一来源记录：

1. `(source_id, external_job_id)`。
2. `(source_id, canonical_url_hash)`。
3. 来源确实没有稳定 ID/URL 时，使用来源内指纹：公司 + 标准化标题 + 标准地点 + 部门，并标记较低置信度。

重复采集更新 `last_seen_at` 和来源字段；内容 Hash 变化时创建版本并触发 `UPDATED`。

### 12.2 跨来源候选匹配

计算候选分数时综合：

- 公司主实体是否相同。
- 外部 ID 是否可被官方来源交叉印证。
- 标准化标题、地点和部门相似度。
- 职责/要求文本 Hash 或文本相似度。
- 发布及更新时间窗口。
- 原始链接是否指向同一官方职位。

处理策略：

- 只有确定性证据才自动关联到同一个 `jobs` 主实体。
- 高相似但无确定性证据的记录写入 `duplicate_candidates`，由管理员确认。
- 低分记录保持独立，宁可暂时重复展示，也不错误合并不同岗位。
- 人工“合并/非重复”结论持久化，后续规则不得反复提出同一候选。
- 阈值和权重在真实样本评估后确定，当前为**待验证**。

## 13. 岗位状态管理

状态含义：

- `NEW`：首次发现，作为短暂事件状态用于“新增”展示。
- `ACTIVE`：来源仍可见且正常招聘。
- `UPDATED`：已存在岗位的关键字段发生变化，作为短暂事件状态。
- `EXPIRED`：超过有效期或连续若干次未发现，但尚不能确认来源已删除。
- `REMOVED`：来源明确返回下架/删除，或经过可靠复核确认不可用。

推荐状态流转：

```text
首次发现 -> NEW -> ACTIVE
ACTIVE -> UPDATED -> ACTIVE
ACTIVE/UPDATED -> EXPIRED -> ACTIVE（重新发现）
ACTIVE/EXPIRED -> REMOVED -> ACTIVE（重新开放）
```

实现要求：

- `NEW` 和 `UPDATED` 的展示依赖事件/时间窗口，不应永久停留；Worker 在规则时间后转回 `ACTIVE`。
- 不能因一次列表缺失就下架。使用连续完整采集缺失次数、最后发现时间和详情复查综合判断。
- 来源采集失败或分页不完整时，不执行缺失下架判断。
- 如果官方页面明确返回已关闭，可转 `REMOVED`；普通 404 仍需区分临时错误。
- 多来源岗位只有在所有有效来源均失效后，主岗位才变为 `EXPIRED`/`REMOVED`。
- 缺失次数、过期天数因来源差异配置，首批来源接入时验证。

## 14. 定时任务设计

MVP 任务类型：

- 来源列表发现任务。
- 岗位详情补全任务。
- 标准化与入库任务。
- 缺失岗位复核和状态更新任务。
- `NEW` / `UPDATED` 事件状态归位任务。
- 数据质量检查、旧任务和日志清理任务。

执行机制：

- Scheduler 根据来源配置向 `ingest_tasks` 写任务。
- Worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务，设置租约和心跳，确保多 Worker 不重复执行。
- 每个任务有幂等键、最大重试次数、下一次执行时间和死信状态。
- 来源级并发和 QPS 独立配置；默认串行或极低并发。
- 使用 PostgreSQL advisory lock 防止同一来源同周期重复调度。
- 任务失败采用带抖动的指数退避，并按来源错误率自动暂停；恢复需人工或健康探测确认。
- 支持管理员手动触发单个来源，但仍遵守限速和合规配置。
- 初期建议每天数次采集，而非分钟级；具体频率依据来源允许范围和岗位变化频率确定。

## 15. API 设计

公开 API 统一前缀建议为 `/api/v1`，只暴露页面所需字段。

### 15.1 公开接口

```text
GET /api/v1/jobs
GET /api/v1/jobs/{id}
GET /api/v1/companies
GET /api/v1/companies/{id}
GET /api/v1/facets
GET /healthz
GET /readyz
```

`GET /jobs` 查询参数：

```text
q, company_id, city, salary_min, salary_max,
experience, education, industry, category,
source, published_within_days, sort, cursor, limit
```

要求：

- 默认只返回有效岗位；历史状态需显式查询且可限制为管理端。
- 使用游标分页；若先采用页码分页，必须设置最大页码和 `limit` 上限。
- 排序仅允许白名单字段：相关性、发布时间、首次发现时间。
- 响应包含来源名称和原始链接，但不得包含内部采集配置、原始载荷或管理员字段。
- 错误返回稳定错误码和请求 ID，不泄露堆栈、SQL 或内部地址。

### 15.2 管理接口

```text
POST /admin/session
DELETE /admin/session
GET /admin/crawl-runs
POST /admin/sources/{id}/runs
PATCH /admin/companies/{id}/metadata
PATCH /admin/jobs/{id}
POST /admin/duplicate-candidates/{id}/resolve
GET /admin/audit-logs
```

管理接口使用独立路由、中间件和权限检查。修改操作支持 CSRF 防护、重复提交保护并完整审计。

## 16. 网站页面规划

### 16.1 首页 `/`

- 今日新增、最近 7 天新增和当前有效岗位数量。
- 最新岗位列表。
- 热门公司和热门岗位方向。
- 搜索入口和常用筛选。
- 所有统计明确时间口径，避免将采集延迟误写为真实发布时间。

### 16.2 岗位搜索 `/jobs`

- 关键词搜索和组合筛选。
- 已选条件可见并可单项清除。
- URL 保存查询条件，支持分享和浏览器前进后退。
- 桌面与移动端均可用；结果列表稳定分页，不提供无限制导出。
- 空结果、加载失败、岗位已失效均有明确状态。

### 16.3 岗位详情 `/jobs/{id}`

- 公司、标题、地点、薪资、经验、学历、招聘类型和状态。
- 职责、要求、资格、福利和技能。
- 发布、更新、首次发现和来源信息。
- “查看原始招聘信息”使用安全外链属性，并提示用户以来源站最新信息为准。
- 已过期或下架岗位保留详情但明确标记，不推荐申请。

### 16.4 公司页 `/companies/{id}`

- 公司简介、官网、类型、规模和有来源的标签。
- 当前有效岗位和历史岗位数量。
- 信息来源和最后核验时间；支持管理员修正。

### 16.5 管理页 `/admin/*`

- 登录、采集运行、错误详情、来源启停、数据修正、重复候选和审计。
- 管理端以工作效率为主，不建设复杂运营大屏。

## 17. 安全设计

### 17.1 API 与应用安全

- 所有输入采用结构化解析、类型校验、长度限制、枚举白名单和未知字段处理。
- SQL 使用参数化查询；动态排序和筛选只从白名单映射生成。
- 服务端模板默认转义；富文本只允许经 HTML 白名单清洗后的内容。
- 修改类请求验证 CSRF Token、`Origin` / `SameSite` Cookie 策略。
- 请求体、Header、查询长度、分页数量和处理超时均设上限。
- 对外错误脱敏；日志中不记录密码、Token、完整 Cookie 和隐私内容。
- 设置 CSP、HSTS、`X-Content-Type-Options`、`Referrer-Policy`、点击劫持防护等响应头。
- 原始外链仅允许 `http/https`，存储和跳转前校验，防止 `javascript:` URL 与开放重定向。
- Fetcher 使用域名白名单并限制重定向，防止配置或数据触发 SSRF；阻止访问回环、链路本地和私网地址，除非部署配置明确允许。

### 17.2 管理员安全

- 管理员账号与未来普通用户账号隔离。
- 密码使用 Argon2id 或经过验证的强密码 Hash；参数在实现时基准测试。
- Session 使用高熵随机 Token，服务端保存 Hash，Cookie 设置 `Secure`、`HttpOnly`、`SameSite`。
- RBAC 最少包含只读审计、数据运营和系统管理员角色。
- 登录限流、失败锁定、会话撤销；生产上线前确认是否强制 MFA，当前为**待确认**。
- 来源启停、人工合并、标签认证和权限变更属于敏感操作，必须记录前后值。

### 17.3 数据与供应链安全

- 密钥和密码通过环境变量或生产 Secret 管理服务注入，禁止进入代码与镜像。
- 数据库最小权限，Web、Worker 和迁移账号按需拆分。
- 依赖锁定并在 CI 执行漏洞扫描、静态检查和镜像扫描。
- 备份加密、限制访问，并定期做恢复演练。
- 用户功能上线前完成隐私影响评估；MVP 不收集简历和非必要个人信息。

## 18. 本站 Bot / 反爬保护

采用分层保护，不依赖单一验证码：

- CDN/WAF：连接层与常见攻击规则、基础 DDoS/CC 缓解、恶意 IP 信誉。
- 应用层：IP、会话/用户、路由和成本维度限流。
- 搜索保护：最小关键词长度、复杂查询限制、最大分页、最大时间窗口和执行超时。
- API 保护：公开字段最小化，不提供全量导出和连续可枚举 ID。
- 异常检测：高频翻页、遍历岗位详情、异常 User-Agent、持续空查询和大量失败请求。
- 渐进处置：降速、短期封禁、要求 CAPTCHA、人工封禁；避免直接永久封禁误伤共享 IP。
- 管理接口采用更严格限流和独立访问策略，可选 VPN/IP allowlist，待部署环境确认。
- 限流事件和 WAF 命中纳入监控，但 IP 日志按保留周期处理，避免无限保存。

单实例 MVP 可使用进程内令牌桶，并依赖 CDN/WAF 做全局保护。部署多个 Web 实例后，引入 Redis 或网关级共享限流。CAPTCHA 仅在滥用指标达到阈值时启用。

## 19. 数据质量与人工修正机制

### 19.1 质量规则

- 必填完整率：公司、标题、来源 URL、来源标识、首次/最后发现时间。
- 合法性：URL、日期顺序、薪资上下限、经验上下限和枚举范围。
- 新鲜度：来源上次成功时间、有效岗位最后发现时间。
- 异常波动：单次新增、更新、下架数量相较历史基线突变。
- 解析漂移：字段空值率突然上升、详情长度异常、选择器失效。
- 重复质量：来源内冲突、跨来源候选积压和人工误判抽样。

### 19.2 人工修正

- 修正采用覆盖层，不直接丢弃原始来源值。
- 每次修正记录字段、原值、新值、原因、操作者和时间。
- 人工锁定字段不会被后续采集覆盖；可显式撤销并回到来源值。
- 跨来源合并支持“确认重复”“确认非重复”“暂缓”三种结果。
- 公司敏感标签必须展示证据来源和核验时间；过期后进入待复核。
- 管理员可查看岗位版本差异和状态变更原因。

## 20. 日志、监控和告警

### 20.1 日志

- JSON 结构化日志，包含时间、级别、服务、请求 ID、任务 ID、来源 ID 和错误类别。
- HTTP 访问日志不记录敏感查询内容；管理员操作另写审计日志。
- 采集错误记录状态码、阶段和摘要，不默认保存完整响应正文。
- 日志由容器输出到 stdout，生产环境交由日志平台收集和设置保留周期。

### 20.2 指标

- HTTP：请求数、状态码、P50/P95/P99 延迟、限流次数、并发数。
- 数据库：连接池使用、慢查询、事务失败和任务积压。
- 采集：每来源成功率、耗时、请求数、重试、解析失败、最近成功时间。
- 数据变化：新增、更新、失效、重复候选和字段完整率。
- Worker：任务成功/失败/重试/死信、租约超时和队列延迟。

### 20.3 告警

- 来源连续失败或超过预期时间未成功。
- 解析成功但岗位数量骤降/骤增。
- 任务积压、死信增长或 Worker 无心跳。
- Web 5xx 比例、延迟或数据库连接异常。
- 备份失败和恢复演练失败。
- 管理员登录暴力尝试、异常导览和限流激增。

具体阈值先以基线观测为准，避免在没有流量数据时编造固定值。

## 21. Docker 部署方案

### 21.1 镜像

- 多阶段构建 Go 二进制，最终镜像使用最小非 root 运行时。
- `web` 和 `worker` 使用同一镜像、不同启动命令，减少构建差异。
- 固定依赖并生成可追溯版本信息；镜像标签包含提交标识。
- 文件系统尽量只读，临时目录和权限显式声明。

### 21.2 Compose 服务

```text
web       Go HTTP 服务
worker    调度与采集 Worker
postgres  主数据库
redis     可选，默认不启用
proxy     本地可选；生产通常由托管 CDN/反向代理承担
```

部署步骤：

1. 校验环境变量和依赖连通性。
2. 单独执行数据库迁移，成功后再滚动启动应用。
3. 启动 Web，确认 readiness 后接入流量。
4. 启动 Worker，并确认来源调度和任务锁正常。
5. 执行冒烟测试和指标检查。

数据卷仅用于数据库；应用容器保持无状态。生产 PostgreSQL 优先使用托管服务。每日备份、保留周期、异地副本和恢复时间目标均为**待确认**。

## 23. 每个任务的优先级

- **P0：MVP 阻塞项**。缺失则不能安全、正确地上线，包括工程基线、数据模型、首个来源、去重状态、公开体验、管理认证、安全、部署和验收。
- **P1：MVP 质量项**。应在正式公开前完成；若内测时间受限，可在不影响数据正确性和安全的前提下缩减界面范围，包括更多来源、运营效率和完整监控面板。
- **P2：上线后增强项**。不阻塞首版，例如独立搜索引擎、Redis 共享缓存、用户订阅和 AI 能力。

## 24. 开发顺序

推荐按以下顺序逐模块推进：

1. **工程可运行**：T01 → T02，建立可重复启动和测试基线。
2. **数据可落地**：T03 → T04，先确认模型、约束和事务。
3. **单来源闭环**：T05 → T06 → T07 → T08，用一个合规来源验证完整流水线。
4. **数据正确性**：T09，基于真实样本修正去重、版本和状态规则。
5. **扩展性验证**：T10，接入第二、第三来源，确认没有把来源细节泄漏到核心模块。
6. **用户可用**：T11 → T12，完成搜索、详情和公司页面。
7. **运营可控**：T13 → T14，确保管理员能处理失败、修正和审计。
8. **上线准备**：T15 → T16 → T17 → T18，完成安全、监控、恢复和验收。

每个任务均要求：先阅读相关代码和测试、说明修改范围、实现最小闭环、运行局部测试，再运行当时已有的完整测试套件。

## 25. MVP 验收标准

### 25.1 功能验收

- 至少 2 个经合规确认的官方来源可按计划运行；目标为 3 个，若来源授权未确认则不得为了数量降级合规要求。
- 从采集到页面展示的端到端链路可重复运行，重复执行不会重复插入同一来源岗位。
- 岗位内容变化会生成版本和 `UPDATED` 事件，重新采集无变化不会制造更新。
- 采集失败不会批量误判岗位下架；满足来源规则后可进入 `EXPIRED` / `REMOVED`。
- 每条展示岗位可追溯到至少一个来源、原始链接及首次/最后发现时间。
- 搜索和筛选覆盖需求列出的 MVP 条件；缺失数据不会被错误显示为确定值。
- 首页、岗位搜索、岗位详情和公司页在主流桌面及移动浏览器可用。
- 管理员可查看运行失败、修正元数据、处理重复候选并查询审计日志。

### 25.2 质量验收

- 核心领域规则和 Adapter 夹具具有单元测试；数据库、采集幂等和状态流转具有集成测试。
- 完整测试套件、静态检查、依赖安全检查和镜像构建通过。
- 使用受控样本人工抽检首批岗位：来源内重复率、关键字段完整率和状态准确性达到上线前设定阈值；阈值需在首个来源 PoC 后用实际数据确定。
- 常规搜索在目标数据量下达到可接受的 P95 响应时间；目标数据量与响应阈值在性能基线任务中确认。
- API 输入限制、参数化 SQL、模板转义、CSRF、管理员认证、限流和 Fetcher SSRF 防护均有验证。
- 数据库备份成功完成至少一次恢复演练。
- 任一来源停用或解析失败不会导致整个 Web 服务不可用。

### 25.3 合规验收

- 每个启用来源均记录获取方式、条款/robots 核验状态、请求策略和最后核验时间。
- 未获确认的招聘平台保持禁用并标记“待确认数据获取方式”。
- 不存在验证码绕过、账号池、代理池规避封禁或访问控制绕过代码。
- 网站展示遵循来源内容授权及必要的归属要求。

## 26. 后续迭代路线图

### 阶段 1A：MVP 稳定化

- 扩展经过确认的官方公司来源和央国企/外企科技岗位。

- 扩展金融、制造、新能源、医疗和教育等行业。

- 当单体在独立扩缩容、故障隔离或团队边界上出现实际瓶颈时，再评估服务拆分。

## 27. 已知风险和待确认问题

### 27.1 数据来源与合规

- **待确认**：首批 2～3 家公司及其公开接口/页面是否允许自动访问、展示和保存职位内容。
- **待确认数据获取方式**：BOSS 直聘、前程无忧、智联招聘。未获得官方 API、开放平台或授权前不开发自动采集。
- **待确认**：各来源 robots、服务条款、内容版权、Logo 使用和原文缓存期限。
- **风险**：招聘站点结构或接口频繁变化，导致解析失败；通过夹具、字段完整率告警和来源隔离降低影响。
- **风险**：来源页面缺少稳定职位 ID，去重和状态判断置信度下降；应保存证据并进入人工审核。

### 27.2 产品与数据口径

- **待确认**：MVP 首批公司名单、目标城市、岗位方向和预计初始岗位规模。
- **待确认**：“最近 10 天”按来源 `published_at`、来源 `updated_at` 还是本站 `first_seen_at` 筛选；建议分别保存并在 UI 明确口径。
- **待确认**：热门公司/方向的统计口径，建议 MVP 使用最近 30 天有效岗位数，不追踪用户行为。
- **待确认**：岗位 `EXPIRED` 的默认时间、连续缺失次数和不同来源差异化规则。
- **待确认**：公司敏感标签采用哪些权威名录和人工核验流程。
- **风险**：跨来源重复判断误合并；默认保守，仅确定性证据自动合并。
- **风险**：薪资、经验和地点表达差异大；标准值和原始值必须并存。

### 27.3 技术与运维

- **待验证**：PostgreSQL 对中文关键词搜索的相关性和性能；首批真实数据上做基准后决定是否需要分词扩展或独立搜索引擎。
- **待确认**：部署云厂商、域名、CDN/WAF、证书、监控和告警接收渠道。
- **待确认**：备份保留周期、RPO、RTO 和恢复演练频率。
- **待确认**：管理员是否必须启用 MFA、是否限制管理端访问网络。
- **风险**：空项目从零建立工程规范容易一次铺设过多；严格按第 24 节逐模块交付。
- **风险**：Worker 和 Web 共用数据库时，异常采集可能挤占连接；使用独立连接池、并发上限和数据库角色隔离。
- **风险**：本站公开后遭到批量抓取；通过 CDN/WAF、查询成本限制、分层限流和异常检测控制，而不是承诺绝对阻断。

### 27.4 下一步开始前必须确认

开始 T08 首个真实来源 Adapter 前，至少确认：

1. 首个来源名称和明确允许的数据获取方式。
2. 允许采集的路径、字段、频率及内容保存/展示范围。
3. MVP 目标部署环境及是否已有 PostgreSQL/CDN/WAF 服务。
4. “最近 10 天”和岗位过期的产品口径。

在上述事项确认前，可以先实施 T01～T07 的通用基础能力，但不得用未经确认的真实来源开展自动采集。
